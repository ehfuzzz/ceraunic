## C. Three things a VC's technical diligence would catch

1. **The product sold ≠ the product built (#12, #13).** EVAL and the decks say heat is station-leg-only with residuals by RFQ on P-A-IDW, and rain uses a weekly PRISM residual. The SPEC, the engine's default house path, Configure.s.sol and the demo screenshot all run a daily temperature pair auction (P-A, which failed Phase 3 at +0.010). P-A-IDW and weekly PRISM rain have no settleable index. Separately, the 0.22 season figure is on the two-leg book; there is no season number for the station-only book that actually ships.
2. **Governance and oracle claims go further than the code (#15, #22, #7).** Memo and deck describe range-bounded, time-locked staker voting; the contracts have a single Ownable owner who can set any cap, window or cooldown instantly, including the 12-day cooldown invariant (#6). The data-release hash is unsigned, so the chain cannot enforce the fixed-vintage rule that only the engine checks (the one skipped parity case), and the mainnet open item the seat ordered is missing from SPEC §17.
3. **Numbers in the SPEC that don't compute (#1, #2, #3, #11).** The only worked waterfall example uses the retired 20 % senior split without saying so, its redeem line evaluates to a different integer than the one printed, the senior-premium base is called net in some places and gross in others, and the tail-charge "never exceeds" claim is false under the floor. Each is small, but a diligence engineer who recomputes the SPEC's own example will find all four in an hour, which hurts the "exact integer parity" pitch.
